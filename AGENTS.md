# Agent Instructions

## Repository purpose

- Mobile-first React and TypeScript app for Zaparoo Core, shipped as iOS and Android apps through Capacitor and as web builds, including the UI embedded in Core.
- Use npm and the Node/npm versions declared in `package.json`. Do not introduce another package manager or lockfile.
- Core communication is JSON-RPC over WebSocket through `src/lib/coreApi.ts` and `src/lib/transport/`.

## Commands

- Install exactly from lockfile: `npm ci`
- Typecheck: `npm run typecheck`
- Lint: `npm run lint`
- Formatting check: `npm run format:check`
- Tests once: `npm run test -- --run`
- Coverage once: `npm run test:coverage -- --run`
- Web-only build: `npm run build:web`
- Core embedded build: `npm run build:core`
- Full native build and Capacitor sync: `npm run build`

`npm run dev`, `npm run dev:server`, and `npm run preview` are long-lived; start them only when asked. `npm run build`, `npm run build:server`, and `npm run sync` can rewrite native projects through Capacitor sync; do not run them as routine validation.

## UI, copy, and accessibility

- Before changing UI, interaction, microcopy, or accessibility behavior, read `docs/design-language.md` and inspect the nearest real screen. Existing app patterns beat generic preferences.
- Reuse WUI primitives under `src/components/wui/`, shared primitives under `src/components/ui/`, `PageFrame`, `SlideModal`, and established row/form patterns. Do not invent decorative cards, badges, icons, helper copy, spacing systems, or loading treatments.
- Preserve safe-area handling, page-heading focus, live announcements, screen-reader behavior, text zoom, swipe-back behavior, focus trapping, and accessible names.
- Use `useHaptics()` or component intent props rather than direct haptic calls.
- Add new user-facing strings to `src/translations/en-US.json`. Other locales fall back; do not mechanically edit every translation file.
- In tests, translation functions return keys. Assert keys rather than English display strings.

## State, API, and routing

- `useStatusStore` owns live Core/app state. `usePreferencesStore` owns ordinary persisted preferences and capability flags; wait for `_hasHydrated` before rendering persistence-dependent UI.
- Use Capacitor Preferences, not `localStorage`, for ordinary persisted settings. Device credentials and other sensitive values belong behind the secure-storage abstraction in `src/lib/crypto/credentials.ts`.
- Transport code owns reconnect, heartbeat, and offline queue behavior. Do not reconnect WebSockets manually from components or feature hooks.
- Extend `CoreAPI` for JSON-RPC behavior and reset it between tests. Preserve compatibility with supported Core versions through existing feature gates.
- Add version gates to `FEATURE_GATES` in `src/lib/featureGates.ts` and use `GatedFeature` or `useCoreFeature` instead of scattering version comparisons.
- `src/routeTree.gen.ts` is generated by the TanStack Router plugin. Never hand-edit it, and keep the router plugin before React in Vite configurations.
- Preserve `/app/` base-path behavior for Core builds and the legacy browser targets and polyfills in `vite.config.ts`.

## Capacitor and native boundaries

- Read `docs/capacitor.md` before changing native behavior, plugins, lifecycle, NFC, safe areas, haptics, storage, discovery, or permissions.
- Guard native-only calls with `Capacitor.isNativePlatform()` and preserve web fallbacks.
- Use the high-level NFC helpers in `src/lib/nfc.ts`; they own session lifecycle and listener cleanup. Do not call `removeAllListeners()` as cleanup.
- Capability checks hydrate cached flags in `usePreferencesStore`; components should consume those flags rather than probing plugins repeatedly.
- Changes to the local MFA bridge span TypeScript, Android, and iOS and require native validation. They cannot ship as a web-only live update.
- Adding or upgrading a Capacitor plugin, changing native code, permissions, or `capacitor.config.ts`, or modifying iOS/Android project configuration requires approval and a store release path.

## Product and release boundaries

- Pro gating is limited to features where phone hardware acts as a Zaparoo reader, such as NFC launch-on-scan, barcode scanning, and shake-to-launch. Purely digital features must remain free.
- Read `docs/deployment.md` before version, live-update, store, signing, or release work.
- Store releases keep package version, lockfile version, Android version, iOS version/build, What's New keys, and validation tests in lockstep. Android and iOS build numbers must match for versioned live-update channels.
- Live updates are only for binary-compatible web assets. Preserve `ready()` rollback protection and use the matching versioned channel, never the legacy shared production channel for current builds.
- Never read, print, copy, or commit `live-update-private.pem`, `.env`, Firebase files, package-registry credentials, store credentials, signing material, or production tokens.
- Do not upload a live update, sync native projects, tag a release, submit a store build, or alter Capawesome Cloud configuration without explicit approval.

## Testing

- Read `docs/testing.md` before adding substantial test infrastructure and `docs/playwright-testing.md` for browser or visual flows.
- Prefer integration tests that exercise real components, stores, API behavior, and user-visible outcomes. Add regression coverage for bug fixes.
- Use shared helpers and factories from `src/test-utils/`, MSW for API behavior, existing Capacitor mocks, accessible Testing Library queries, and `userEvent` for interaction.
- Do not mock the component under test, create fake replacement components, test CSS classes or source text, duplicate implementation logic, or use hardcoded delays.
- Use `findBy*`, `waitFor`, fake timers, and deterministic state reset for async behavior. Preserve automatic `CoreAPI`, MSW, timer, store, and secure-storage cleanup.

## Approval boundaries

Ask before adding dependencies, changing shared infrastructure, making broad refactors, altering feature monetization, changing public Core API expectations, or touching native/release configuration.

## Completion

For normal TypeScript changes, run `npm run typecheck`, `npm run lint`, `npm run format:check`, and `npm run test -- --run`. Run the relevant web/Core build for build-mode changes and native validation only when the task requires it. Report exactly which checks ran and any that were skipped; do not claim completion while a relevant check is failing.

PR descriptions must not include a separate test-plan section.
